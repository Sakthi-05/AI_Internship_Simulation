## 1. Executive Summary

This ADR evaluates synchronization and consensus strategies for maintaining financial consistency across geographically distributed ERP ledger partitions.

The accounting module must support concurrent financial transactions, cross-partition double-entry bookkeeping, asynchronous sub-ledger synchronization, network failures, duplicate message delivery, and out-of-order transaction events.

Three primary approaches are evaluated:

1. Multi-Raft consensus with partition-local transaction commits.
2. Distributed Two-Phase Commit (2PC) coordinated through Raft-replicated transaction state.
3. Hybrid CRDT and eventual-consistency synchronization.

The selected architecture is a hybrid transactional architecture:

- Multi-Raft provides consensus and durable replication for individual ledger partitions.
- Distributed 2PC coordinates transactions that modify multiple authoritative ledger partitions.
- Transaction coordinator state is durably replicated using Raft.
- PostgreSQL stores authoritative journal entries and transaction records.
- Transactional outbox events propagate committed changes to downstream systems.
- CRDTs and eventual consistency are permitted only for non-authoritative derived projections.

The financial ledger will prioritize consistency, durability, and auditability over write availability during a network partition.

No financial transaction may be declared committed until all required participants have durably prepared and a commit decision has been recorded by the replicated coordinator.

## 2. Business Context and Problem Statement

The ERP accounting module maintains financial records across multiple partitions.

Example partitions include:

- Accounts Payable
- Accounts Receivable
- General Ledger
- Inventory Valuation
- Procurement Accounting
- Regional Financial Sub-ledgers

A single business operation may require journal entries in multiple partitions.

Example:

A purchase transaction generates:

- Debit: Inventory Asset
- Credit: Accounts Payable

Both entries must be recorded consistently.

A failure between the two postings could produce an unbalanced financial ledger if the system permits independent commits without coordination.

The system must therefore guarantee:

1. Every committed journal transaction is balanced.
2. Debit totals equal credit totals.
3. A cross-partition transaction is committed everywhere or nowhere.
4. Duplicate messages do not create duplicate financial postings.
5. Out-of-order events cannot silently overwrite authoritative accounting records.
6. Network partitions cannot create two independent authorities for the same ledger partition.
7. Every posting and correction remains traceable for financial audits.

### Core invariants

For every committed journal transaction:

\[
\sum Debits = \sum Credits
\]

For each transaction:

\[
TransactionStatus \in
\{PENDING, PREPARED, COMMITTED, ABORTED\}
\]

A transaction must never transition from COMMITTED to ABORTED.

A posted journal entry must never be physically overwritten or deleted to resolve a conflict.

## 3. Architecture Alternatives

### 3.1 Alternative A — Multi-Raft Consensus

Multi-Raft operates multiple independent Raft groups, generally one group per ledger partition or shard.

Each group elects a leader and replicates its log through a majority quorum.

For a three-voter group:

\[
Quorum = \lfloor 3/2 \rfloor + 1 = 2
\]

For a five-voter group:

\[
Quorum = \lfloor 5/2 \rfloor + 1 = 3
\]

Advantages:

- Strong ordering within each ledger partition.
- Durable replicated transaction logs.
- Automatic leader election when a leader fails.
- Independent scaling of ledger partitions.
- Clear ownership and fencing boundaries.

Limitations:

- Consensus within one Raft group does not automatically provide atomicity across multiple groups.
- A transaction touching two partitions may commit in one group and fail in the other without an additional coordination protocol.
- Cross-partition ordering requires a transaction coordinator or another atomic commit mechanism.

**Decision:** Adopt Multi-Raft as the partition-level consensus foundation, but do not use it alone for cross-partition financial transactions.

### 3.2 Alternative B — Distributed Two-Phase Commit over Raft

Distributed 2PC coordinates transactions across multiple authoritative ledger partitions.

The coordinator communicates with each participant through two phases.

**Phase 1: Prepare**

1. The coordinator creates a unique transaction ID.
2. The transaction is validated.
3. Each participant checks account balances, accounting rules, and transaction constraints.
4. Each participant writes a durable prepare record.
5. Participants vote YES or NO.
6. The coordinator records the prepare outcome in its replicated Raft log.

**Phase 2: Commit or Abort**

- If all participants vote YES, the coordinator records a durable COMMIT decision.
- Otherwise, it records ABORT.
- Participants apply the recorded decision.
- Commit notifications are emitted through transactional outbox records.

Advantages:

- Atomic cross-partition financial posting.
- Prevents partially committed double-entry transactions.
- Preserves ACID transaction semantics across partitions.
- Provides a clear audit trail.
- Works with existing PostgreSQL transactional storage.

Limitations:

- Requires coordination between participants.
- Can increase transaction latency.
- Prepared transactions retain locks and resources.
- A network partition may block transaction completion.
- Coordinator recovery and participant reconciliation are necessary.

**Decision:** Adopt distributed 2PC for transactions that modify multiple authoritative ledger partitions. Replicate coordinator state using Raft to prevent a single coordinator failure from losing the transaction decision.

### 3.3 Alternative C — Hybrid CRDT and Eventual Consistency

Conflict-Free Replicated Data Types allow replicas to merge certain concurrent updates without requiring immediate coordination.

Potential applications:

- Financial dashboards.
- Regional reporting aggregates.
- Non-authoritative expense summaries.
- Read-only analytics.
- Operational metrics.
- Derived reconciliation views.

Advantages:

- High write availability for supported data structures.
- Low-latency local updates.
- Efficient asynchronous synchronization.
- Tolerance of temporary network partitions for derived state.

Limitations:

- Arbitrary financial journal postings are not safely mergeable as independent state updates.
- CRDT convergence does not guarantee cross-partition atomicity.
- Eventual consistency can temporarily expose incomplete financial aggregates.
- A converged projection does not establish that the underlying journal entries were valid or authorized.
- Duplicate or semantically conflicting business events require separate validation.

**Decision:** Use CRDT-style aggregation only for derived, non-authoritative data. Do not use CRDT merging as the commit protocol for authoritative financial journal entries.

## 4. Quantitative Trade-Off Matrix

The following estimates are engineering planning assumptions, not measured production benchmarks.

Assumptions:

- PostgreSQL-backed regional ledger partitions.
- Three-region deployment.
- Inter-region network RTT approximately 80–180 ms.
- Local database processing approximately 5–20 ms.
- Three-voter Raft groups with majority quorum.
- Concurrent financial posting workload.
- No network congestion beyond the stated planning envelope.

| Evaluation criterion | Multi-Raft only | Distributed 2PC over Raft | Hybrid CRDT / Eventual |
|---|---|---|---|
| Single-partition write latency | 10–200 ms | 10–200 ms | 5–30 ms local |
| Cross-partition write latency | Not guaranteed atomic | Approximately 200–500 ms typical planning estimate | 5–30 ms local, asynchronous convergence |
| High-load throughput | High per independent shard | Lower due to coordination and locks | High for supported derived updates |
| Cross-partition atomicity | No | Yes | No |
| Consistency | Strong within each group | ACID-style coordinated commit | BASE/eventual |
| Partition tolerance | Majority quorum required | Prepared transactions may block | High availability for supported operations |
| Split-brain protection | Raft quorum and fencing | Raft quorum plus transaction decision recovery | Requires application-level conflict rules |
| Duplicate prevention | Log/index deduplication | Transaction ID and idempotency key | Event ID and merge semantics |
| Recovery objective | Approximately 1–5 minutes | Approximately 1–5 minutes, depending on prepared transactions | Approximately 1–15 minutes for projection convergence |
| Audit suitability | High | Very high | Insufficient as authoritative journal |
| Operational complexity | High | Very high | Medium to high |

### 4.1 Latency model

For distributed 2PC:

\[
T_{2PC} \approx T_{prepare} + T_{decision} + T_{apply}
\]

A simplified cross-region planning model is:

\[
T_{2PC} \approx 2R + T_{database} + T_{replication}
\]

Where:

- \(R\) = inter-region network round-trip time.
- \(T_{database}\) = validation and database processing.
- \(T_{replication}\) = additional durable replication overhead.

For an RTT of 120 ms, database processing of 20 ms, and additional replication overhead of 100 ms:

\[
T_{2PC} \approx 2(120) + 20 + 100
\]

\[
T_{2PC} \approx 360ms
\]

This is a simplified planning estimate. Actual latency depends on coordinator placement, participant count, replication topology, parallelism, WAL flush behavior, and network conditions.

### 4.2 Throughput model

Let:

- \(N\) = available ledger partitions.
- \(W\) = sustainable single-partition write capacity.
- \(C\) = fraction of transactions requiring cross-partition coordination.

An approximate throughput planning model is:

\[
Throughput \approx
\frac{N \times W}{1 + C \times K}
\]

Where \(K\) represents coordination overhead under the target workload.

This is a capacity-planning heuristic, not a universal performance law. It must be calibrated using realistic load tests.

To improve throughput:

- Keep transactions partition-local whenever business rules permit.
- Batch independent non-authoritative projection updates.
- Execute participant prepare requests concurrently.
- Minimize the number of participants per transaction.
- Use connection pooling.
- Apply bounded retries with exponential backoff.
- Monitor prepared transaction duration and lock contention.

### 4.3 Recovery Time Objectives

Proposed initial targets:

| Failure | Target |
|---|---|
| Single Raft leader failure | 5–30 seconds for leader election, subject to tuning |
| Coordinator process failure | 1–5 minutes for recovery and reconciliation |
| Participant process failure | 1–5 minutes, depending on database recovery |
| Temporary network partition | Recovery after quorum and communication return |
| Derived projection recovery | 1–15 minutes |
| Audit record reconstruction | Complete from durable authoritative journal and replicated logs |

These are service objectives to validate through failure-injection testing, not guaranteed protocol properties.

## 5. CAP Theorem and Network Partition Policy

During a network partition, the financial ledger cannot simultaneously guarantee unrestricted write availability and strong consistency.

The selected architecture prioritizes consistency and partition tolerance for authoritative financial writes.

### Scenario A: Healthy network

- Raft groups maintain majority quorum.
- The coordinator communicates with all required participants.
- All participants prepare successfully.
- The coordinator durably records COMMIT.
- Participants apply the commit.
- Outbox events are published.

Result: Transaction committed.

### Scenario B: Coordinator loses contact with one participant

- The coordinator cannot obtain every required YES vote.
- No COMMIT decision is issued.
- The transaction remains pending or is aborted according to its durable coordinator state.
- The user receives a pending or failed response.

Result: No partial successful financial posting.

### Scenario C: Coordinator crashes after all participants prepare

- Participants retain durable prepared records.
- A replacement coordinator recovers the replicated transaction state.
- The replacement determines whether a COMMIT or ABORT decision was durably recorded.
- Participants receive the recovered decision.

Result: Participants do not invent independent decisions.

### Scenario D: Split-brain partition

- Only the Raft majority may elect a valid leader.
- Minority nodes cannot authorize new financial commits.
- Ownership epochs and fencing tokens prevent an old leader from continuing writes.
- Cross-partition transactions remain blocked if any required participant cannot establish valid authority.

Result: Fail closed for authoritative ledger writes.

### Scenario E: No quorum

No new authoritative writes are accepted.

The system may continue serving explicitly marked stale or read-only reporting views, but it must not present those views as authoritative current balances.

## 6. Automated Conflict-Resolution Protocol

Financial conflicts must be resolved using deterministic accounting rules rather than last-write-wins or arbitrary CRDT merging.

### 6.1 Transaction identity

Every transaction must carry:

- transaction_id
- idempotency_key
- source_event_id
- ledger_partition_id
- account_id
- partition_sequence
- ownership_epoch
- accounting_period
- effective_date
- created_at
- committed_at
- currency
- debit_amount
- credit_amount
- source_reference
- actor_id

### 6.2 Duplicate transaction handling

A unique constraint must prevent repeated processing of the same idempotency key within its defined scope.

Example:

```sql
CREATE UNIQUE INDEX uq_ledger_idempotency
ON ledger_transactions (ledger_partition_id, idempotency_key);
```

If a previously committed transaction is received again:

1. Locate the existing transaction.
2. Verify the request payload matches the original.
3. Return the original result.
4. Do not insert another journal entry.

If the same idempotency key is reused with different financial content, reject it and record an audit event.

### 6.3 Out-of-order event handling

Wall-clock timestamps must not be used as the sole ordering mechanism.

Use:

1. Source partition sequence.
2. Transaction ID.
3. Ownership epoch.
4. Explicit dependency references.
5. Accounting effective date.

The system must distinguish between:

- Event arrival time.
- Event creation time.
- Financial effective date.
- Authoritative commit order.

An event arriving late must not overwrite an already committed journal entry.

If a late transaction affects an earlier accounting period:

- Validate the accounting period status.
- Apply the appropriate period-adjustment policy.
- Record a linked adjustment or reversal.
- Preserve the original entry.
- Record the actor, reason, and approval.
- Recalculate derived balances.

### 6.4 Conflicting financial entries

If two events attempt to modify the same financial business operation:

1. Compare transaction IDs and source references.
2. Check idempotency keys.
3. Validate source authorization.
4. Verify ownership epoch.
5. Verify account and period constraints.
6. Check whether either entry has already committed.
7. Reject duplicate or semantically conflicting postings.
8. Route unresolved conflicts to an authorized reconciliation workflow.

Never automatically discard one valid-looking financial posting based solely on timestamp ordering.

### 6.5 Split-brain recovery

Every partition maintains a monotonically increasing ownership epoch.

Before accepting a write, the ledger validates that the writer's epoch matches the currently authorized epoch.

When leadership changes:

- The old owner is fenced.
- The new owner obtains authority through a valid quorum.
- The database candidate is independently checked for durable WAL history.
- Previously acknowledged transactions must be preserved.
- Prepared transactions are resolved using the durable coordinator decision.

Raft consensus and PostgreSQL WAL replication are separate mechanisms. A Raft majority alone does not prove that the promoted PostgreSQL database contains every acknowledged financial commit.

### 6.6 Immutable correction policy

Committed journal entries are never deleted or silently modified.

Corrections use:

- Reversal entries.
- Adjustment entries.
- Linked replacement entries.
- Explicit audit references.

Every correction retains the original transaction reference and reason.

### 7.2 Core services

**Transaction API**

- Accepts financial posting requests.
- Validates authentication and authorization.
- Enforces idempotency.
- Creates transaction IDs.
- Returns transaction status.

**Transaction Coordinator**

- Maintains transaction state.
- Executes 2PC.
- Stores decisions durably.
- Uses a Raft-replicated control log.
- Recovers incomplete transactions.

**Partition Participant**

- Validates ledger ownership.
- Checks accounting constraints.
- Writes prepare records.
- Applies commit or abort decisions.
- Emits durable outbox events.

**Conflict Resolution Service**

- Detects duplicate source events.
- Identifies out-of-order sequences.
- Validates ownership epochs.
- Routes ambiguous conflicts for manual review.
- Creates adjustment and reversal workflows.

**Projection Synchronization Service**

- Consumes committed outbox events.
- Updates non-authoritative reporting views.
- Supports replay and reconciliation.
- Uses version-aware event processing.
