
# Multi-Region ERP Inventory Consistency: Architectural Trade-off Analysis

**Status:** Proposed  
**Difficulty:** Intermediate  
**System:** Enterprise Supply Chain ERP  
**Scope:** Multi-region inventory synchronization, warehouse sharding, and distributed consistency  
**Final Recommendation:** Hybrid consistency model using local strong consistency and cross-region eventual consistency.

---

## 1. Executive Summary

The Enterprise Supply Chain ERP operates across multiple geographically distributed warehouse nodes. Each warehouse manages inventory updates, stock reservations, order fulfillment, returns, and transfers.

As the system expands across regions, maintaining accurate inventory becomes challenging because of network latency, concurrent stock updates, replication delays, and network partitions.

Three consistency approaches are evaluated:

1. Eventual consistency using CQRS and event sourcing.
2. Strong consistency using distributed transactions and consensus protocols.
3. Hybrid consistency combining local strong consistency with cross-region eventual consistency.

**Final recommendation:** Adopt a hybrid consistency architecture.

Each warehouse's PostgreSQL shard remains the authoritative owner of its inventory. Stock reservations and deductions are executed through local database transactions with row-level locking and version checks. Cross-region updates are propagated asynchronously through durable events.

This approach provides accurate stock allocation while allowing global inventory visibility without requiring every warehouse operation to wait for a distributed transaction.

## 2. System Context and Existing Architecture

The consistency model builds upon the previously established ERP architecture:

- PostgreSQL stores authoritative inventory and transaction records.
- Inventory is geographically sharded by warehouse or regional ownership.
- Supplier routing selects suitable fulfillment warehouses.
- Redis Cluster provides high-frequency inventory read caching.
- FastAPI exposes inventory, routing, and fulfillment services.
- Warehouse nodes communicate through asynchronous inventory events.

### Architectural Principles

1. Every inventory item has one authoritative warehouse owner.
2. PostgreSQL remains the source of truth.
3. Redis is a disposable cache, not an authoritative inventory database.
4. Inventory mutations must be transactional and idempotent.
5. Cross-region synchronization must tolerate delayed and duplicated events.
6. A network partition must never allow two regions to independently sell the same stock.

## 3. Consistency Models

### 3.1 Eventual Consistency

Eventual consistency allows updates to propagate asynchronously between regions.

A warehouse commits its inventory changes locally. The change is then published as an event and consumed by other regions.

CQRS (Command Query Responsibility Segregation) separates write operations from read operations.

Event sourcing records inventory changes as an ordered sequence of events.

Example:

1. Warehouse A receives an order for 10 units.
2. Its PostgreSQL transaction deducts 10 units.
3. An InventoryDeducted event is recorded.
4. The event publisher distributes the event.
5. Warehouse B updates its regional inventory projection.
6. Regional availability views eventually reflect the change.

**Advantages**

- Low local write latency.
- High availability during temporary inter-region network failures.
- Independent scaling of read and write workloads.
- Efficient cross-region event distribution.
- Complete event history for auditing and reconstruction.

**Disadvantages**

- Replication lag can expose stale stock quantities.
- Duplicate or out-of-order events require handling.
- Concurrent purchases may oversell stock if regions independently allocate the same inventory.
- Read projections may temporarily disagree.
- Event replay and reconciliation add operational complexity.

**Best use cases**

- Global inventory dashboards.
- Reporting and analytics.
- Non-binding stock availability searches.
- Warehouse performance monitoring.
- Inventory movement history.

### 3.2 Strong Consistency

Strong consistency ensures that a successful operation is reflected consistently before another dependent operation proceeds.

Distributed Two-Phase Commit (2PC) and consensus protocols such as Raft are possible approaches.

#### Two-Phase Commit

2PC coordinates a transaction across multiple database participants.

**Phase 1: Prepare**
- The coordinator asks participating databases to prepare the transaction.
- Each participant checks constraints and locks required resources.
- Participants vote to commit or abort.

**Phase 2: Commit**
- If all participants vote to commit, the coordinator sends COMMIT.
- Otherwise, it sends ABORT.

**Advantages**

- Coordinated transaction outcomes across participating databases.
- Useful when an operation genuinely requires atomic updates across multiple systems.
- Prevents a partially committed distributed transaction when participants follow the protocol correctly.

**Disadvantages**

- Higher transaction latency.
- Participants may remain blocked while waiting for the coordinator.
- Network failures can leave transactions in a prepared state.
- Reduced availability during partitions.
- Increased operational and recovery complexity.

#### Consensus Using Raft

Raft maintains a replicated state machine through leader election and majority-based log replication.

**Advantages**

- Provides a consistent ordering of replicated state changes.
- Supports leader election after node failures.
- Prevents two independent leaders from committing conflicting entries under the protocol's quorum assumptions.
- Useful for strongly consistent coordination metadata.

**Disadvantages**

- Writes require communication with a quorum.
- Cross-region quorum communication increases latency.
- Minority partitions cannot commit new entries.
- Consensus infrastructure requires careful deployment and monitoring.
- Applying consensus to every inventory operation can become expensive.

**Best use cases**

- Global inventory ownership metadata.
- Warehouse ownership transfers.
- Critical coordination records.
- Operations that genuinely require atomic multi-region agreement.

### 3.3 Hybrid Consistency

Hybrid consistency combines strong consistency for critical stock mutations with eventual consistency for cross-region read models.

Each warehouse maintains authoritative inventory locally. Other regions receive inventory events asynchronously.

For example:

1. Warehouse A owns SKU-1001.
2. Warehouse A processes a reservation using a PostgreSQL transaction.
3. The transaction locks the inventory row and validates available stock.
4. The stock quantity and version are updated atomically.
5. An event is recorded in the transactional outbox.
6. Other regions receive the event asynchronously.
7. Their read projections and caches are refreshed.

A reservation at another warehouse must be validated against that warehouse's authoritative inventory, not against a remote cached quantity.

**Advantages**

- Accurate local inventory mutations.
- Lower write latency than global distributed transactions.
- High read scalability.
- Better resilience to temporary inter-region partitions.
- Clear separation between authoritative data and replicated projections.

**Disadvantages**

- Global inventory views can temporarily be stale.
- Requires event processing, idempotency, and reconciliation.
- Cross-warehouse transfers require explicit coordination.
- The application must distinguish advisory availability from confirmed reservations.

## 4. Architectural Trade-off Matrix

Scores range from 1 (weak) to 5 (strong) for this ERP use case.

| Evaluation Criterion | Eventual Consistency | Strong Consistency | Hybrid Consistency |
|---|---:|---:|---:|
| Local write latency | 5 | 2 | 5 |
| Global data accuracy | 2 | 5 | 4 |
| Read scalability | 5 | 3 | 5 |
| Partition availability | 5 | 1 | 4 |
| Overselling prevention | 2 | 5 | 5 |
| Implementation simplicity | 3 | 1 | 3 |
| Cross-region synchronization | 4 | 3 | 4 |
| Recovery flexibility | 4 | 2 | 5 |
| Overall ERP suitability | 3 | 3 | 5 |

### Analysis

Eventual consistency offers high availability and scalability but cannot independently guarantee safe stock allocation.

Strong consistency provides coordinated updates but introduces substantial latency and availability costs across geographically separated regions.

Hybrid consistency provides the strongest overall balance because it protects authoritative inventory mutations without requiring all read operations to wait for global synchronization.

## 5. Quantitative Latency and Accuracy Analysis

The following figures are illustrative engineering estimates for architectural comparison, not measured production benchmarks.

Assumptions:

- Three geographic regions.
- Regional network round-trip time: approximately 40–120 ms.
- Local PostgreSQL transaction latency: approximately 5–15 ms under normal load.
- Redis cache read latency: approximately 1–5 ms within the application region.
- Peak workload: 5,000 inventory read requests per second and 500 inventory write requests per second across the system.
- Replication and event delivery operate asynchronously for eventual read models.

### Estimated Write Latency

| Operation | Eventual Model | Strong Global Model | Hybrid Model |
|---|---:|---:|---:|
| Local inventory write | 5–15 ms | 120–400 ms | 5–15 ms |
| Cross-region propagation | 50–500 ms | Included in commit coordination | 50–500 ms |
| Local reservation validation | 5–15 ms | 120–400 ms | 5–15 ms |
| Remote availability projection | 50–500 ms stale window | Consistent after committed transaction | 50–500 ms stale window |

Actual latency depends on topology, database implementation, quorum placement, transaction size, and workload.

### Accuracy and Risk Analysis

| Scenario | Eventual Consistency | Strong Consistency | Hybrid Consistency |
|---|---|---|---|
| Concurrent reservation at same warehouse | Requires additional safeguards | Strong coordination | Protected by local transaction |
| Concurrent reservation across regions | Overselling risk without ownership controls | Prevented through coordinated transaction | Prevented through inventory ownership |
| Delayed replication | Stale read possible | Reduced after successful commit | Stale read possible in projections |
| Duplicate event | Requires deduplication | Not applicable to synchronous commit in the same way | Handled through idempotent consumers |
| Network partition | Local writes can continue | Majority/quorum requirements restrict writes | Local owner can continue safe local operations |
| Global availability accuracy | Temporarily stale | Stronger consistency at higher cost | Temporarily stale, with authoritative validation |

### Interpretation

The main performance advantage of the hybrid model is that local reservations avoid waiting for inter-region coordination.

The main correctness safeguard is that every stock mutation is checked against the authoritative warehouse inventory.

A stale availability projection may display an outdated quantity, but it cannot authorize a reservation.

## 6. Recommended Inventory Ownership Model

Adopt geographic inventory ownership.

Each warehouse or regional shard owns the authoritative inventory records for its stock.

Example:

| Warehouse | Region | Inventory Authority |
|---|---|---|
| WH-BLR-01 | India South | PostgreSQL Shard A |
| WH-MUM-01 | India West | PostgreSQL Shard B |
| WH-SIN-01 | Southeast Asia | PostgreSQL Shard C |
| WH-FRA-01 | Europe | PostgreSQL Shard D |

Each inventory record should include:

- warehouse_id
- sku_id
- available_quantity
- reserved_quantity
- version
- updated_at

A warehouse may serve global customers, but it must not allow another region to directly mutate its authoritative inventory.

## 7. Inventory Mutation and Event Synchronization

### 7.1 Local Transaction

A stock deduction should use a transaction with row-level locking.

Example:

```sql
BEGIN;

SELECT available_quantity, version
FROM warehouse_inventory
WHERE warehouse_id = :warehouse_id
  AND sku_id = :sku_id
FOR UPDATE;

-- Validate available_quantity >= requested_quantity.

UPDATE warehouse_inventory
SET available_quantity = available_quantity - :requested_quantity,
    version = version + 1
WHERE warehouse_id = :warehouse_id
  AND sku_id = :sku_id;

COMMIT;
```

The application must reject insufficient stock and ensure that reservation and movement records are committed consistently.

### 7.2 Transactional Outbox

The transactional outbox pattern ensures that database changes and corresponding events are recorded together.

Within one PostgreSQL transaction:

1. Update the inventory record.
2. Increment its version.
3. Insert an inventory event into the outbox table.
4. Commit the transaction.

A background publisher reads committed outbox records and sends them to the event system.

This avoids the failure scenario where the database update succeeds but the event is never published.

### 7.3 Event Structure

Example event:

```json
{
  "event_id": "evt-10001",
  "event_type": "InventoryDeducted",
  "warehouse_id": "WH-BLR-01",
  "sku_id": "SKU-1001",
  "quantity_changed": -10,
  "version": 109,
  "timestamp": "2026-11-18T10:30:00Z"
}
```

Consumers must:

- Check event IDs to prevent duplicate processing.
- Check versions to prevent applying older updates after newer ones.
- Update their local read projections.
- Invalidate or refresh Redis cache entries.
- Record processing failures for retry.

## 8. Network Partition and Split-Brain Failure Analysis

A network partition occurs when geographically distributed nodes cannot communicate reliably.

Split-brain occurs when multiple nodes behave as though they are independently authoritative.

This is particularly dangerous for inventory because two regions might accept orders against the same physical stock.

### Failure Scenario 1: Inter-Region Network Partition

**Situation:**

Warehouse A cannot communicate with Warehouse B.

**Risk:**

Warehouse B may have an outdated projection of Warehouse A's inventory.

**Mitigation:**

- Warehouse A remains the sole owner of its inventory.
- Warehouse B cannot directly reserve Warehouse A's stock.
- Warehouse B may display its last known availability with a stale-data indicator.
- Any reservation request must be validated by the owning warehouse.

### Failure Scenario 2: Duplicate Inventory Events

**Situation:**

The event publisher retries an event after failing to receive an acknowledgement.

**Risk:**

The same deduction could be applied twice to a read projection.

**Mitigation:**

- Assign a unique event ID.
- Maintain an event-consumer deduplication record.
- Use monotonic inventory versions.
- Apply each event only once.
- Replay failed events safely.

### Failure Scenario 3: Two Regions Attempt to Allocate the Same Stock

**Situation:**

Two regional services receive requests for the same inventory.

**Risk:**

Both services may read an available quantity of 20 and attempt to allocate 15 units.

**Mitigation:**

- Assign one authoritative owner to the inventory record.
- Route reservations to that owner.
- Use PostgreSQL row-level locking.
- Validate stock before committing.
- Reject the second request if insufficient stock remains.

### Failure Scenario 4: Warehouse Owner Becomes Unavailable

**Situation:**

The authoritative database shard becomes unreachable.

**Risk:**

Other regions may attempt to accept orders using stale replicated inventory.

**Mitigation:**

- Stop confirming reservations for the unavailable inventory.
- Allow non-binding availability displays only with freshness information.
- Retry requests using idempotency keys.
- Do not automatically promote an asynchronous read replica to an independent inventory owner.
- Use a controlled ownership-transfer process after recovery or failover.

### Failure Scenario 5: Regional Leader Failure

**Situation:**

A region uses a consensus-based coordination service and its leader fails.

**Risk:**

Requests may be delayed during leader election.

**Mitigation:**

- Elect a new leader using the consensus protocol.
- Require a majority quorum for authoritative coordination changes.
- Reject writes from minority partitions.
- Recover the committed log before resuming coordination.
- Verify inventory ownership and database versions before restoring service.

## 9. Split-Brain Recovery Strategy

The system must prevent two regions from becoming active owners of the same inventory shard.

Recommended recovery procedure:

1. Detect loss of communication or database health.
2. Mark the affected region as degraded.
3. Stop new reservations that require the unavailable owner.
4. Preserve the last committed inventory version and event offset.
5. Restore connectivity or perform a controlled failover.
6. Verify the authoritative database state.
7. Replay missing committed events.
8. Reconcile inventory projections across regions.
9. Invalidate outdated Redis cache entries.
10. Resume reservations after ownership and consistency checks succeed.

### Ownership Protection

Use a controlled ownership epoch or fencing token.

Every ownership change increments the epoch.

A write request must carry the current valid ownership epoch. Requests from an old owner are rejected after ownership has changed.

This prevents a previously isolated region from continuing to write after a new owner has been activated.

Ownership changes should be coordinated through a reliable control plane, not inferred merely from a timeout.

## 10. Replication Lag Tolerances

Not all ERP operations require identical freshness.

Recommended initial objectives:

| Operation | Consistency Requirement | Suggested Target |
|---|---|---|
| Local stock reservation | Strong consistency | Validate in the owning database transaction |
| Stock deduction | Strong consistency | Commit atomically in the owning database |
| Local inventory display | Near-current | Cache freshness target of 1–5 seconds where feasible |
| Cross-region availability search | Eventual consistency | Typical projection lag target below 500 ms |
| Global inventory reporting | Eventual consistency | Lag target below 5 seconds |
| Inventory audit history | Durable event history | No committed event loss |
| Warehouse ownership transfer | Strong coordination | Complete only after ownership fencing and validation |

These are proposed service objectives, not guaranteed performance measurements. They must be validated through load testing and operational monitoring.

### Replication Lag Monitoring

Track:

- Event creation timestamp.
- Event publication timestamp.
- Consumer processing timestamp.
- Current database inventory version.
- Current projection version.
- Outbox backlog.
- Consumer retry count.

If replication lag exceeds the configured threshold, the UI should mark the data as stale and reservation requests should continue to validate against the authoritative database.

## 11. Redis Cache Integration

Redis Cluster remains a read optimization layer.

Recommended behavior:

1. Read from Redis for frequently requested stock availability.
2. On a cache miss, query the owning PostgreSQL shard.
3. Store the returned quantity with its inventory version.
4. After a committed inventory update, publish an invalidation event.
5. Delete or refresh the corresponding cache entry.
6. Prevent older events or delayed readers from overwriting newer cache versions.

### Cache Consistency Rules

- Redis is never the authority for stock reservations.
- Cache entries must include warehouse and inventory version.
- Use bounded TTLs.
- Use version-aware invalidation.
- Avoid using cached values to approve deductions.
- Flush or rebuild cache entries after uncertain recovery events.

This is consistent with the previously recommended Redis Cluster cache-aside architecture.

## 12. Final Architectural Recommendation

Adopt the hybrid consistency model.

### Strong Consistency Within Each Inventory Owner

Use PostgreSQL transactions, row-level locks, version checks, and idempotency keys for:

- Stock reservations.
- Inventory deductions.
- Returns and adjustments.
- Local warehouse stock transfers.
- Inventory ownership changes.

### Eventual Consistency Across Regions

Use event sourcing and CQRS for:

- Global inventory projections.
- Cross-region stock visibility.
- Reporting and analytics.
- Warehouse dashboards.
- Inventory movement history.

### Coordination for Critical Cross-Warehouse Operations

When an order requires inventory from multiple warehouses:

1. Route each allocation to its authoritative warehouse.
2. Reserve stock independently at each owner.
3. Use a central order workflow or saga to track the overall operation.
4. If one reservation fails, release other reservations through compensating actions.
5. Make every step idempotent and auditable.
6. Confirm the order only after the required allocations have succeeded.

Avoid using a global 2PC transaction for every order unless a genuine atomic multi-database requirement exists and its latency and availability costs are acceptable.

## 13. Final Decision Matrix

| Design Area | Selected Approach | Reason |
|---|---|---|
| Inventory authority | Geographic PostgreSQL ownership | Clear responsibility for each stock record |
| Local stock writes | Strong consistency | Prevent overselling |
| Cross-region synchronization | Eventual consistency | Lower latency and better partition resilience |
| Event distribution | Transactional outbox | Reliable publication of committed changes |
| Read architecture | CQRS projections | Scale read-heavy workloads |
| Event history | Event sourcing | Auditability and replay |
| Distributed cache | Redis Cluster | Fast inventory reads and controlled invalidation |
| Cache correctness | Version-aware invalidation | Prevent stale cache overwrites |
| Cross-warehouse workflow | Saga pattern | Coordinate independent reservations |
| Ownership failover | Fencing tokens and controlled recovery | Prevent split-brain writes |

## 14. Conclusion

A fully eventual consistency model is scalable but introduces unacceptable risks if stale inventory values are used to authorize stock reservations.

A fully strong global consistency model provides stronger coordination but adds significant latency and reduces write availability during network partitions.

The hybrid model is the most suitable architecture for the multi-region ERP system.

By combining authoritative PostgreSQL transactions, geographic inventory ownership, asynchronous event propagation, CQRS read projections, and Redis caching, the system can maintain accurate stock allocation while supporting high-throughput global inventory queries.

**Final decision:** Strong consistency for authoritative inventory mutations, eventual consistency for cross-region read models, and controlled ownership coordination for failover and multi-warehouse workflows.
