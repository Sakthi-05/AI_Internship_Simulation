## 1. Executive Summary

This document defines the consensus quorum and failure detection tuning policy for the global ERP inventory platform.

The system operates across geographically distributed regions. Each warehouse inventory shard has one authoritative write owner. Raft coordinates ownership changes, while PostgreSQL maintains the authoritative inventory ledger and replicates committed transactions through WAL.

The main challenge is balancing:

- Partition tolerance.
- Regional write availability.
- Leader election speed.
- Network jitter.
- Split-brain prevention.
- Strict read-after-write consistency.
- Zero data loss for acknowledged inventory commitments.

The selected policy is:

1. Use fixed majority voting for Raft consensus.
2. Support three-region and five-region deployments.
3. Use Raft joint consensus for safe membership changes.
4. Avoid dynamically changing quorum weights during failures.
5. Tune heartbeat and election intervals using measured WAN round-trip time and jitter.
6. Use short, bounded leadership leases with conservative clock assumptions.
7. Require infrastructure-enforced fencing before promoting a new inventory owner.
8. Require synchronous PostgreSQL durability before acknowledging critical inventory writes.
9. Reject critical writes when quorum or durability cannot be verified.

The recommended default configuration is a three-region Raft deployment with a two-of-three majority quorum. Five-region deployments use a three-of-five majority quorum when greater fault tolerance is required.

## 2. Existing Architecture

The current ERP architecture contains:

| Component | Responsibility |
|---|---|
| FastAPI | Inventory and reservation APIs |
| PostgreSQL | Authoritative inventory ledger |
| PostgreSQL WAL | Durable replication |
| Raft | Leader election and ownership coordination |
| Redis Cluster | Regional read caching |
| Transactional outbox | Reliable event publication |
| Saga orchestrator | Cross-region transaction recovery |
| CQRS projections | Eventually consistent global views |
| Reconciliation workers | Post-failover recovery |

### 2.1 Consistency requirements

The architecture maintains the following rules:

- One authorized write owner per warehouse shard.
- Inventory reservations and deductions use local PostgreSQL transactions.
- Acknowledged critical writes require synchronous durability.
- Redis is never used to authorize inventory reservations.
- Global projections may be eventually consistent.
- Strict read-after-write requests must be served from the authoritative owner or a replica that has confirmed the required commit position.
- A new owner must be authorized through consensus and fencing.

### 2.2 Scope

This ADR tunes the consensus control plane and its interaction with database failover.

It does not replace:

- PostgreSQL WAL replication.
- Saga orchestration.
- Inventory ledger transaction logic.
- Existing shard ownership rules.

## 3. Quorum Model Evaluation

A quorum is the minimum number of voting members required to approve a consensus decision.

For a cluster of N voting members, a fixed majority quorum is:

\[
Q = \left\lfloor \frac{N}{2} \right\rfloor + 1
\]

The maximum number of failed voting members tolerated is:

\[
F = N - Q
\]

This ensures that two independent majorities cannot exist simultaneously under the same Raft configuration.

### 3.1 Three-region deployment

For three voting members:

\[
N=3
\]

\[
Q=\lfloor 3/2 \rfloor+1=2
\]

\[
F=3-2=1
\]

| Available Voters | Quorum | Ownership Changes |
|---|---|---|
| 3 | 2 | Allowed |
| 2 | 2 | Allowed |
| 1 | 2 | Blocked |
| 0 | 2 | Blocked |

Advantages:

- Lower coordination overhead.
- Relatively fast leader election.
- Tolerates one unavailable voter.
- Suitable for a three-region deployment.

Limitation:

Two unavailable voters prevent new leader election.

### 3.2 Five-region deployment

For five voting members:

\[
N=5
\]

\[
Q=\lfloor 5/2 \rfloor+1=3
\]

\[
F=5-3=2
\]

| Available Voters | Quorum | Ownership Changes |
|---|---|---|
| 5 | 3 | Allowed |
| 4 | 3 | Allowed |
| 3 | 3 | Allowed |
| 2 | 3 | Blocked |
| 1 | 3 | Blocked |

Advantages:

- Tolerates two unavailable voters.
- Better resilience against multiple regional failures.
- More flexible placement across independent failure domains.

Disadvantages:

- More WAN coordination.
- Higher operational cost.
- More complex membership management.
- Potentially higher commit latency.

### 3.3 Quorum comparison

| Evaluation | 3 Regions | 5 Regions |
|---|---:|---:|
| Voters | 3 | 5 |
| Majority quorum | 2 | 3 |
| Tolerated failures | 1 | 2 |
| Coordination overhead | Lower | Higher |
| WAN dependency | Moderate | Higher |
| Operational complexity | Moderate | High |
| Recommended use | Standard deployment | High-resilience deployment |

### 3.4 Selected quorum strategy

**Use fixed majority quorums.**

- Three-region deployment: two-of-three.
- Five-region deployment: three-of-five.

The five-region configuration should be introduced only when the additional failure tolerance justifies its operational and latency costs.

The quorum must not be reduced dynamically during a partition simply to restore write availability.

## 4. Weighted and Dynamic Quorum Evaluation

Weighted quorum systems assign different voting weights to members.

A weighted design can prioritize selected regions, but it introduces additional complexity.

Potential problems:

- Incorrect weight configuration can produce unsafe quorum overlap.
- A region may gain disproportionate control over ownership decisions.
- Dynamic weight changes during failures can create inconsistent views of membership.
- Weighted voting is not automatically equivalent to standard Raft majority voting.

### 4.1 Decision matrix

| Criteria | Fixed Majority | Weighted Quorum | Dynamic Quorum |
|---|---:|---:|---:|
| Safety reasoning | 5 | 3 | 2 |
| Operational simplicity | 5 | 2 | 2 |
| Failure predictability | 5 | 3 | 2 |
| Regional flexibility | 3 | 5 | 5 |
| Implementation complexity | 5 | 2 | 1 |
| Standard Raft compatibility | 5 | 2 | 2 |

### 4.2 Decision

Fixed majority voting is selected for the production consensus policy.

Membership changes must use Raft's joint-consensus procedure or an implementation-supported equivalent.

During joint consensus, decisions must satisfy the quorum requirements of both the old and new configurations.

No emergency weight adjustment is permitted merely because a region becomes unreachable.

## 5. Heartbeat and Election Timeout Model

Raft leaders send periodic heartbeats to followers to maintain leadership.

If followers stop receiving heartbeats within the configured election timeout, they may begin a new election.

Timeouts must account for:

- WAN round-trip time.
- Network jitter.
- Packet loss.
- Temporary congestion.
- Scheduling delays.
- Garbage collection or process pauses.
- Cross-region routing changes.

### 5.1 Mathematical model

Define:

- \(H\): heartbeat interval.
- \(RTT_{p99}\): measured 99th-percentile network round-trip time.
- \(J_{p99}\): measured 99th-percentile additional jitter.
- \(P\): processing and scheduling margin.
- \(E\): election timeout.

A proposed heartbeat interval is:

\[
H = \max(250ms,\ RTT_{p99}/2)
\]

The heartbeat interval must also be bounded by the selected Raft implementation's timing requirements.

A conservative election timeout is:

\[
E_{min} = \max(5H,\ 2RTT_{p99}+J_{p99}+P)
\]

For randomized election timeouts:

\[
E \sim Uniform(E_{min}, 1.5E_{min})
\]

Randomization reduces the chance of repeated simultaneous elections.

These formulas are initial engineering heuristics, not universal Raft guarantees. Actual settings must be validated against the implementation, WAN measurements, and failure tests.

### 5.2 Example network assumptions

Illustrative cross-region measurements:

| Parameter | Assumed Value |
|---|---:|
| WAN RTT p50 | 80 ms |
| WAN RTT p95 | 130 ms |
| WAN RTT p99 | 180 ms |
| Additional jitter p99 | 60 ms |
| Processing margin | 40 ms |

Using the proposed model:

\[
H=\max(250,\ 180/2)=250ms
\]

\[
E_{min}=\max(5(250),\ 2(180)+60+40)
\]

\[
E_{min}=\max(1250,\ 460)=1250ms
\]

Therefore:

\[
E \sim Uniform(1250ms,\ 1875ms)
\]

### 5.3 Recommended initial configuration

| Parameter | Three-Region Deployment | Five-Region Deployment |
|---|---:|---:|
| Heartbeat interval | 250 ms | 300 ms |
| Minimum election timeout | 1.25 s | 1.5 s |
| Maximum randomized timeout | 1.875 s | 2.25 s |
| Missed-heartbeat threshold | 5 | 5 |
| Failure confirmation | Multiple independent signals | Multiple independent signals |

These are initial tuning values for the assumed network conditions, not fixed production guarantees.

For cross-continental deployments with higher RTT or jitter, recalculate the parameters using measured latency distributions.

### 5.4 Timeout tuning policy

The platform must:

1. Measure WAN latency continuously.
2. Track p50, p95, and p99 RTT.
3. Detect sustained jitter increases.
4. Alert when election timeouts approach observed network delays.
5. Tune parameters through controlled configuration rollout.
6. Avoid automatically shortening election timeouts during congestion.

Election timeouts that are too short create unnecessary leadership changes. Timeouts that are too long increase recovery time.

## 6. Leadership Lease and Expiration Policy

A leadership lease limits how long a leader may act as the authorized owner without renewing its authority.

Leases are useful for reducing unnecessary coordination, but they are not a substitute for Raft consensus or fencing.

### 6.1 Lease model

Define:

- \(L\): lease duration.
- \(H\): heartbeat interval.
- \(R\): renewal interval.
- \(\epsilon\): maximum clock uncertainty.
- \(D\): maximum assumed message and scheduling delay.

A proposed lease duration is:

\[
L = 3E
\]

The renewal interval is:

\[
R = H
\]

A conservative safety condition is:

\[
L > 2\epsilon + D + R
\]

A leader must stop accepting new critical writes before its locally calculated lease expiration, leaving sufficient safety margin for clock uncertainty and message delay.

### 6.2 Initial lease values

| Parameter | Three Regions | Five Regions |
|---|---:|---:|
| Heartbeat interval | 250 ms | 300 ms |
| Lease duration | 3.75 s | 4.5 s |
| Renewal interval | 250 ms | 300 ms |
| Clock uncertainty budget | 50 ms | 50 ms |
| Expiration safety margin | 250 ms | 300 ms |

These values assume bounded clock uncertainty and timely heartbeat processing.

If the clock uncertainty or network-delay assumptions cannot be maintained, lease-based write authorization must be disabled or the lease must be made more conservative.

### 6.3 Lease expiration behavior

When a leader cannot renew its authority:

1. Stop accepting new critical inventory writes.
2. Complete or safely abort in-flight transactions according to their durable commit state.
3. Mark the shard unavailable for new commitments.
4. Allow Raft election to establish a new owner.
5. Require fencing of the old owner.
6. Resume writes only after the new owner passes all validation checks.

## 7. Strict Read-After-Write Consistency

The ERP platform requires users to observe their own acknowledged inventory commits.

A successful reservation must not be followed by a stale read that reports the previous available quantity.

### 7.1 Read policy

Three read categories are defined.

| Read Type | Source | Consistency |
|---|---|---|
| Critical reservation confirmation | Authoritative PostgreSQL owner | Strong |
| Read immediately after acknowledged write | Primary or replica confirmed through commit position | Read-after-write |
| Global availability dashboard | CQRS projection or Redis | Eventual |

### 7.2 Read-after-write token

After a successful write, the API returns a consistency token containing:

- Warehouse ID.
- Ownership epoch.
- Commit or transaction version.
- Relevant WAL commit position where available.

Example:

```json
{
  "warehouse_id": "WH-101",
  "ownership_epoch": 102,
  "inventory_version": 87,
  "consistency": "read_after_write"
}
```

A subsequent read must:

1. Route to the authoritative owner, or
2. Wait until the selected replica has replayed the required commit position.

If the required position is unavailable, the API must not silently return stale data as if it were current.

### 7.3 Redis behavior

Redis is not used for strict read-after-write confirmation.

After a critical inventory mutation:

- Invalidate the affected cache entry.
- Use a version-aware cache refill.
- Reject stale cache values when their version is older than the required version.
- Route strict reads to the authoritative database if the cache cannot satisfy the requested version.

## 8. Simultaneous Dual-Region Partition Analysis

Consider a five-region deployment:

- Region A: current leader.
- Region B: synchronous database standby.
- Region C: Raft voter and asynchronous replica.
- Region D: Raft voter.
- Region E: Raft voter.

The quorum is three of five.

### 8.1 Scenario A: A and B become isolated from C, D, and E

The cluster divides into:

- Partition 1: A and B.
- Partition 2: C, D, and E.

The second partition retains three-of-five Raft quorum.

However, it cannot automatically assume that it has the latest durable PostgreSQL inventory data.

Required behavior:

1. A loses contact with the majority and cannot renew leadership.
2. C, D, and E establish a new consensus leader.
3. The old primary is fenced.
4. The candidate database's WAL position is verified.
5. If all acknowledged critical writes are present, promotion may proceed.
6. If acknowledged writes are missing, promotion is blocked until safe recovery is established.

An asynchronous replica must never be promoted under a zero-data-loss claim merely because it has won the Raft election.

### 8.2 Scenario B: A and B fail, while C, D, and E remain connected

- Three voters remain.
- Quorum is maintained.
- A new leader may be elected.
- The candidate database is verified.
- Critical writes resume after promotion and fencing.

If the remaining replica does not contain all acknowledged critical commits, RPO=0 cannot be claimed.

### 8.3 Scenario C: A, B, and C become isolated from D and E

The partitions contain:

- Partition 1: three voters.
- Partition 2: two voters.

The first partition has a majority and may elect a new leader.

The two-voter partition cannot elect an independent leader.

The new database owner still requires verification of durable inventory history and fencing of the former primary.

### 8.4 Scenario D: Two regions fail simultaneously

For five voters:

\[
N=5,\ Q=3,\ F=2
\]

The remaining three voters can maintain quorum if they can communicate.

If the two failed regions include the primary and synchronous standby, the remaining asynchronous replicas may be behind.

Therefore:

- Raft quorum may survive.
- Inventory write availability may not.
- Zero RPO may not be achievable until the acknowledged WAL history is recovered.

This distinction is mandatory in the failover policy.

### 8.5 Scenario E: No partition has a majority

If no connected partition contains at least three of five voters:

- No new leader can be elected.
- Existing leases expire.
- Critical writes stop.
- Read-only access may continue where safe.
- Recovery waits for quorum restoration.

## 9. Zero Data Loss Guarantee

RPO=0 is a data durability guarantee, not a consensus voting property.

The system may claim zero data loss for acknowledged critical writes only when:

1. The PostgreSQL transaction has committed.
2. The required synchronous standby has durably flushed the corresponding WAL.
3. The commit acknowledgement was returned only after the configured durability condition was satisfied.
4. Failover promotion verifies that the candidate contains the acknowledged commit history.
5. The former primary is fenced.

If the synchronous standby is unavailable, the system must either:

- Pause critical inventory writes, or
- Enter a separately approved degraded mode with an explicitly weaker RPO.

The default production policy is to pause critical writes.

No asynchronous replica may be promoted with an unconditional RPO=0 guarantee.

## 10. Automated Recovery and Reconciliation

After a leader change, the recovery worker performs the following steps.

### Phase 1: Establish ownership

- Verify the Raft leader.
- Obtain the latest ownership epoch.
- Fence the old primary.
- Verify database promotion eligibility.

### Phase 2: Validate database durability

- Compare known WAL positions.
- Verify synchronous replication acknowledgements.
- Check recovery state.
- Confirm the candidate contains all acknowledged commits.

### Phase 3: Reconcile inventory

Compare:

- Physical stock.
- Reserved stock.
- Inventory version.
- Ledger transaction sequence.
- Reservation identifiers.

### Phase 4: Recover outbox events

- Find undelivered events.
- Replay missing events.
- Ignore duplicate event IDs.
- Preserve per-aggregate ordering.

### Phase 5: Recover Saga workflows

- Find interrupted supply-chain commitments.
- Verify reservation status.
- Resume incomplete operations.
- Compensate invalid or expired reservations.
- Retry compensation using original idempotency keys.

### Phase 6: Restore read paths

- Invalidate stale Redis keys.
- Rebuild regional cache entries.
- Refresh CQRS projections.
- Validate read-after-write behavior.

### Phase 7: Record recovery

Generate a recovery report containing:

- Election term.
- New leader identity.
- Ownership epoch.
- Recovered WAL position.
- Replication lag.
- Reconciliation mismatch count.
- Saga recovery count.
- Compensation results.
- Actual RPO and RTO.

## 11. Python Quorum Validation Prototype

The following Python example demonstrates fixed majority quorum validation.

It is an architectural prototype, not a production Raft implementation.

```python
from dataclasses import dataclass
from typing import List


@dataclass
class QuorumResult:
    total_nodes: int
    available_nodes: int
    required_quorum: int
    can_elect_leader: bool
    tolerated_failures: int


def calculate_quorum(total_nodes: int) -> int:
    if total_nodes < 1:
        raise ValueError("At least one voter is required")

    return total_nodes // 2 + 1


def evaluate_quorum(
    total_nodes: int,
    available_nodes: int,
) -> QuorumResult:

    if available_nodes < 0 or available_nodes > total_nodes:
        raise ValueError("Invalid available node count")

    required = calculate_quorum(total_nodes)

    return QuorumResult(
        total_nodes=total_nodes,
        available_nodes=available_nodes,
        required_quorum=required,
        can_elect_leader=available_nodes >= required,
        tolerated_failures=total_nodes - required,
    )


def evaluate_partition(
    regions: List[str],
    total_nodes: int,
):

    print(f"\nCluster size: {total_nodes}")
    print(f"Required quorum: {calculate_quorum(total_nodes)}")

    for region in regions:
        result = evaluate_quorum(
            total_nodes,
            int(region),
        )

        print({
            "available": result.available_nodes,
            "quorum": result.required_quorum,
            "leader_election_allowed": result.can_elect_leader,
        })


if __name__ == "__main__":

    for cluster_size in (3, 5):

        print(f"\nTesting {cluster_size}-region deployment")

        for available in range(cluster_size + 1):

            result = evaluate_quorum(
                cluster_size,
                available,
            )

            print(
                f"Available={available}, "
                f"Required={result.required_quorum}, "
                f"Leader Election={result.can_elect_leader}"
            )
```

### Expected behavior

For three voters:

- Two or three available voters permit consensus.
- Zero or one available voter blocks new leadership.

For five voters:

- Three, four, or five available voters permit consensus.
- Zero, one, or two available voters block new leadership.

The prototype evaluates voter availability only. A production failover controller must additionally verify membership configuration, quorum communication, fencing, WAL durability, and replica eligibility.

## 12. Security and Operational Controls

Required controls:

- Mutual TLS between Raft members.
- Authenticated and authorized membership changes.
- Encryption of PostgreSQL replication traffic.
- Separate replication and inventory write credentials.
- Ownership epoch validation.
- Infrastructure-level fencing.
- Audit logging of elections and promotions.
- Protected configuration changes.
- Clock synchronization monitoring.
- Monitoring for excessive clock drift.
- Alerts for repeated leader elections.
- Restricted manual override procedures.

Clock uncertainty must be monitored if leases are used.

If the clock uncertainty exceeds the configured safety budget, lease-dependent write authorization must be suspended.

## 15. Final Decision

The ERP platform will use fixed majority Raft quorums with measured, conservative timing parameters.

### Selected configuration

| Parameter | Three Regions | Five Regions |
|---|---:|---:|
| Voters | 3 | 5 |
| Quorum | 2 | 3 |
| Tolerated voter failures | 1 | 2 |
| Heartbeat | 250 ms | 300 ms |
| Election timeout range | 1.25–1.875 s | 1.5–2.25 s |
| Lease duration | 3.75 s | 4.5 s |
| Clock uncertainty budget | 50 ms | 50 ms |
| Critical inventory RPO | 0 under synchronous durability | 0 under synchronous durability |
| Regional failover RTO | ≤ 15 minutes target | ≤ 15 minutes target |

### Final policy

1. Fixed majority quorums are mandatory.
2. Raft joint consensus is required for membership changes.
3. Dynamic quorum reduction during partitions is prohibited.
4. Heartbeat and election parameters must be derived from measured WAN latency and jitter.
5. Leadership leases must use bounded clock assumptions and conservative expiration margins.
6. Infrastructure fencing is mandatory before regional promotion.
7. PostgreSQL WAL durability must be validated independently of Raft quorum.
8. Critical writes pause when zero-data-loss durability cannot be guaranteed.
9. Strict read-after-write requests bypass stale Redis and lagging replicas.
10. Interrupted supply-chain commitments are recovered through idempotent Saga workflows.

## 16. Conclusion

This policy establishes a mathematically defined and operationally testable consensus configuration for global ERP inventory failover.

Fixed majority quorums prevent two independent partitions from authorizing conflicting leaders under the same membership configuration. Conservative heartbeat and election timeout settings reduce unnecessary leader changes under WAN jitter. Bounded leases and infrastructure-enforced fencing protect against stale ownership.

Most importantly, consensus and database durability are treated as separate requirements.

Raft determines who may own a shard. PostgreSQL determines which inventory transactions are durable. Saga determines how interrupted business commitments recover.

The system intentionally pauses critical inventory writes when it cannot preserve both ownership safety and zero-data-loss durability.

**Final principle: Never weaken quorum or durability guarantees simply to make a regional inventory shard appear available.**
