# Warehouse Location Strategy and Inventory Shard Balancing

**System:** Enterprise Resource Planning (ERP)\
**Related capability:** Supplier tiering and multi-warehouse order
routing\
**Document type:** Technical decision record\
**Status:** Proposed\
**Task:** Evaluate and propose warehouse location strategy for inventory
shard balancing

------------------------------------------------------------------------

## 1. Executive Summary

This document proposes a warehouse-location and inventory-sharding
framework for an ERP platform operating across multiple geographic
regions. The objective is to reduce order-fulfillment latency while
maintaining accurate, available, and auditable inventory across regions.

Two primary sharding strategies are evaluated:

1.  **Geographic sharding:** inventory is assigned to a regional shard
    based on the warehouse's physical region.
2.  **Demand-based sharding:** inventory is assigned or partitioned
    according to demand patterns, product velocity, and order
    destinations rather than geography alone.

The recommended approach is a **geographic-first hybrid**. Each
warehouse belongs to a regional inventory shard, while demand forecasts
and product-velocity data guide stock placement within and across those
regions. A designated primary fulfillment node is selected per order
using eligibility checks followed by a weighted score for delivery time,
available stock, fulfillment cost, and operational reliability. A
secondary node is retained as a fallback.

This approach keeps inventory ownership and database routing
understandable, supports regional growth, and avoids the coordination
overhead of making every stock movement globally distributed.

## 2. Goals and Non-Goals

### Goals

-   Minimize expected order-to-delivery and order-to-dispatch latency.
-   Support inventory visibility across multiple regions.
-   Keep stock ownership clear and prevent overselling.
-   Scale reads and writes as warehouses, products, and order volume
    grow.
-   Support the existing supplier-tiering and order-routing service.
-   Provide deterministic primary-node selection and documented fallback
    behavior.
-   Preserve auditability for transfers, reservations, receipts, and
    adjustments.

### Non-goals

-   Selecting exact real-world warehouse addresses without demand,
    carrier, and cost data.
-   Replacing supplier selection logic. Supplier tiering determines
    sourcing preference; warehouse routing determines where available
    inventory should fulfill an order.
-   Guaranteeing globally strong consistency for every inventory read.
    The design instead defines a single authoritative owner for each
    inventory balance.

**Available stock** must be calculated as:

`available_quantity = on_hand_quantity - reserved_quantity - safety_stock`

If safety stock is not configured for a SKU/warehouse pair, the
configured default is used. A node is not eligible to fulfill an order
if available quantity is insufficient, the warehouse is inactive, the
SKU is blocked, or the node cannot meet mandatory service constraints.

## 4. Warehouse Distribution Layout Options

### Option A --- Centralized distribution

One primary distribution center serves all regions, with limited
satellite stock.

**Advantages** - Simplest inventory ownership and database design. -
Consolidated safety stock and easier cycle counting. - Lower initial
warehouse setup and technology cost.

**Disadvantages** - Longer delivery distances for remote customers. - A
single node can become a capacity bottleneck or failure point. -
Cross-region shipping increases transport cost and latency.

This is appropriate for a small operation with geographically
concentrated demand, but it is not the preferred long-term layout for a
multi-region ERP.

### Option B --- Regional distribution nodes

Create a fulfillment node for each major demand region. Each node owns
the inventory physically stored at that location.

**Advantages** - Shorter last-mile and regional delivery distances. -
Clear regional inventory ownership. - Regional outages can be isolated
more easily. - Regional reporting and replenishment can be scaled
independently.

**Disadvantages** - More facilities, duplicated safety stock, and higher
operating cost. - Requires inter-warehouse transfer planning. -
Inventory visibility must aggregate data from multiple regional owners.

This is the preferred base layout when demand is distributed across
multiple regions.

### Option C --- Regional hubs with demand-driven satellites

Use regional hubs for broad SKU coverage and smaller satellite or
forward-stock locations for high-velocity products near concentrated
demand.

**Advantages** - Balances regional coverage with local delivery speed. -
Fast-moving SKUs can be positioned near demand hotspots. - Slow-moving
inventory can remain consolidated at hubs.

**Disadvantages** - More complex replenishment and transfer policies. -
Requires reliable demand forecasting and SKU segmentation. - More
complex operational and data coordination than a pure regional model.

This is a suitable evolution path after regional demand patterns are
measurable.

## 5. Inventory Sharding Strategies

### Strategy 1 --- Geographic sharding

Partition inventory records by the warehouse's assigned region. Each
warehouse and its stock balances have one authoritative regional shard.

Example logical mapping:

  Region key   Inventory shard     Example ownership
  ------------ ------------------- -----------------------------------
  `IN-SOUTH`   `inventory_south`   Warehouses serving southern India
  `IN-WEST`    `inventory_west`    Warehouses serving western India
  `IN-NORTH`   `inventory_north`   Warehouses serving northern India
  `IN-EAST`    `inventory_east`    Warehouses serving eastern India

The region-to-shard mapping should be maintained in a central
routing/configuration registry. The application resolves a warehouse's
region to its authoritative shard before reading or writing its
inventory.

**Benefits** - Aligns database locality with physical inventory
ownership. - Makes regional writes and operational failures easier to
isolate. - Supports region-specific scaling and data residency
requirements. - Provides predictable routing for stock mutations.

**Risks** - Demand may be uneven, causing a hot region or hot shard. -
Orders spanning regions may require distributed reads or coordinated
reservations. - Moving a warehouse between regions requires a controlled
data migration.

### Strategy 2 --- Demand-based sharding

Partition inventory by demand characteristics, such as product category,
SKU velocity, customer segment, or demand cluster. High-volume SKUs can
be distributed across separate partitions to spread write and read load.

Example logical mapping:

  -----------------------------------------------------------------------
  Demand class            Partitioning approach   Typical use
  ----------------------- ----------------------- -----------------------
  High velocity           Dedicated or split      Frequently ordered
                          partitions by SKU hash  products
                          / demand cluster        

  Medium velocity         Shared partitions by    Predictable recurring
                          product family          demand

  Low velocity            Consolidated shared     Rarely ordered products
                          partition               
  -----------------------------------------------------------------------

**Benefits** - Can distribute load from high-volume SKUs. - Supports
product-specific scaling. - May improve query performance for workload
patterns concentrated around particular product groups.

**Risks** - Physical warehouse ownership becomes less intuitive. - A
single order may touch multiple partitions. - Rebalancing SKU partitions
can be operationally complex. - Stock transfers and reservations require
careful coordination across demand partitions. - Demand changes can make
the original partition strategy suboptimal.

Demand-based partitioning is useful as a database optimization when
measured hot spots justify it, but it should not replace the warehouse
as the authoritative owner of physical stock.

### Strategy 3 --- Hybrid geographic ownership with demand-aware placement

Use geographic sharding as the source-of-truth boundary and demand
forecasting to determine where inventory should be positioned. Within a
region, high-volume SKUs may use optimized indexing, partitioning,
caching, or dedicated capacity if telemetry demonstrates a need.

**Benefits** - Preserves clear physical stock ownership. - Places
fast-moving stock near demand. - Avoids cross-region writes for ordinary
inventory operations. - Allows targeted scaling without making the
logical stock model demand-dependent.

**Risks** - Requires demand forecasting and periodic placement
reviews. - Transfers between regions must be modeled as explicit
outbound and inbound movements. - Regional inventory aggregation is
eventually consistent if it reads from multiple shards.

**Recommendation:** Adopt the hybrid strategy, with geographic sharding
as the authoritative inventory ownership model and demand-aware
placement as the optimization layer.

### Interpretation

-   **Centralized** has the lowest initial infrastructure and database
    complexity but is weakest for multi-region latency and resilience.
-   **Geographic** provides a strong balance between locality, scale,
    and clear stock ownership.
-   **Demand-based** can distribute database load effectively but
    introduces cross-partition coordination and weaker alignment with
    physical stock.
-   **Hybrid** provides the best expected fulfillment performance while
    preserving geographic stock ownership, at the cost of additional
    planning and operational complexity.

These are qualitative design scores, not measured production benchmarks.
They should be revisited using actual order, carrier, and warehouse
telemetry.

## 7. Primary Fulfillment Node Selection Logic

### 7.1 Eligibility gates

Before scoring candidates, the routing service must exclude a warehouse
if any mandatory condition fails:

1.  Warehouse is active and accepting orders.
2.  Warehouse is in a supported fulfillment region for the order.
3.  SKU is stocked and not blocked or quarantined.
4.  Available quantity is at least the requested quantity, or the order
    explicitly permits split fulfillment.
5.  Capacity is available for the requested dispatch window.
6.  Estimated delivery time is within the order's hard maximum, if one
    is specified.
7.  Inventory data is sufficiently fresh for a reservation decision.

A candidate that fails an eligibility gate must not win solely because
it is cheaper.

### 7.2 Weighted candidate score

For eligible candidates, calculate normalized values from 0 to 1:

-   `delivery_score`: lower estimated delivery time receives a higher
    score.
-   `availability_score`: higher available quantity relative to
    requested quantity receives a higher score, capped at 1.
-   `cost_score`: lower estimated fulfillment cost receives a higher
    score.
-   `reliability_score`: higher on-time fulfillment performance receives
    a higher score.
-   `capacity_score`: more available fulfillment capacity receives a
    higher score.

Proposed initial weights:

  Criterion                              Weight
  ---------------------------------- ----------
  Estimated delivery time                   35%
  Available stock / stock coverage          25%
  Fulfillment and transport cost            20%
  Operational reliability                   15%
  Remaining node capacity                    5%
  **Total**                            **100%**

`candidate_score = 0.35 * delivery_score + 0.25 * availability_score + 0.20 * cost_score + 0.15 * reliability_score + 0.05 * capacity_score`

Weights are configurable by service level or product class. For urgent
orders, delivery-time weight can increase. For low-margin products, cost
weight may increase, provided service-level constraints remain
satisfied.

### 7.3 Primary and secondary node selection

1.  Resolve the destination to its preferred service region.
2.  Retrieve eligible warehouses from the regional routing registry and
    any permitted neighboring-region fallback list.
3.  Read candidate stock and operational capacity.
4.  Apply eligibility gates.
5.  Calculate the weighted score for each eligible node.
6.  Select the highest-scoring node as primary.
7.  Select the next-highest eligible node as secondary.
8.  Reserve stock atomically at the authoritative inventory shard.
9.  If reservation fails due to a concurrent stock change, refresh
    availability and retry selection a bounded number of times.
10. If no single node can fulfill the order and split fulfillment is
    allowed, create a multi-node allocation plan.

Tie-breakers should be deterministic: lower estimated delivery time,
then lower total cost, then stable warehouse ID order.

## 8. Multi-Region Inventory Data Model and Consistency

Recommended logical entities:

-   `Warehouse(id, region_id, status, service_area, capacity)`
-   `InventoryBalance(warehouse_id, sku_id, on_hand, reserved, safety_stock, version, updated_at)`
-   `InventoryMovement(id, warehouse_id, sku_id, movement_type, quantity, reference, created_at)`
-   `WarehouseRegion(region_id, shard_key, routing_priority)`
-   `FulfillmentAllocation(order_id, warehouse_id, sku_id, quantity, status)`
-   `InventoryTransfer(transfer_id, source_warehouse_id, destination_warehouse_id, sku_id, quantity, status)`

### Ownership and consistency rules

-   A warehouse's physical stock balance has exactly one authoritative
    shard.
-   Stock mutations are written to the owning shard, not to a global
    aggregate.
-   Use database transactions and row-level locking (for example,
    `SELECT ... FOR UPDATE`) when reserving or changing stock.
-   Use an idempotency key for reservation and transfer commands to
    prevent duplicate effects on retries.
-   Maintain an append-only movement history for audit and
    reconciliation.
-   Regional/global inventory summaries may be asynchronously
    aggregated, but must be labeled with their update time and must not
    be used as the sole authority for final reservation.
-   Cross-region transfers should use a state machine:
    `REQUESTED -> DISPATCHED -> IN_TRANSIT -> RECEIVED`, with explicit
    failure/cancellation handling. Do not simply decrement one region
    and increment another without a traceable transfer record.
-   Avoid distributed transactions across regional shards for ordinary
    order routing. Prefer a reservation workflow with explicit
    compensation if a multi-node allocation partially fails.

## 10. Implementation Guidance for the ERP Backend

The existing supplier tiering and order routing service should remain
responsible for supplier preference and sourcing alternatives. Warehouse
selection should be a separate service boundary that consumes the
requisition/order requirements and candidate inventory data.

Suggested service responsibilities:

-   `WarehouseRegistry`: resolves regions, service areas, and shard
    ownership.
-   `InventoryAvailabilityService`: reads authoritative and summarized
    stock.
-   `WarehouseScoringService`: applies eligibility gates and weighted
    scoring.
-   `FulfillmentRoutingService`: selects primary/secondary nodes and
    constructs split allocations.
-   `ReservationService`: commits stock reservations at the owning
    shard.
-   `TransferService`: manages inter-warehouse transfer state.
-   `RoutingAuditService`: records candidate scores, exclusions, chosen
    node, and fallback reason.

Suggested API contract:

`POST /routing/warehouse-selection`

Request fields: - `order_id` - `destination_region` or destination
postal code - `items`: SKU and requested quantity - `max_delivery_hours`
(optional) - `allow_split_fulfillment` (boolean) - `service_level`
(standard / expedited)

Response fields: - `routing_status` (recommended / reserved /
partially_fulfilled / unfulfilled) - `primary_warehouse_id` -
`secondary_warehouse_ids` - `allocations` (warehouse, SKU, quantity) -
`estimated_delivery_hours` - `score_breakdown` - `fallback_reason` -
`inventory_snapshot_timestamp`

The endpoint should distinguish a recommendation from a committed
reservation. A successful recommendation must not be represented as a
completed allocation unless the reservation transaction succeeds.

## 12. Final Recommendation

Adopt a **regional warehouse layout with geographic inventory sharding
and demand-aware stock placement**.

The geographic shard should be the authoritative owner of each
warehouse's physical inventory. Demand forecasts should determine which
SKUs and quantities are positioned at regional hubs and, where
justified, satellite nodes. The routing service should first apply hard
eligibility rules and then select the highest-scoring warehouse using
delivery time, stock coverage, cost, reliability, and capacity.

For every order, choose a primary node and a secondary fallback. Commit
reservations only against the authoritative inventory owner. If the
primary fails eligibility or reservation, retry against the next
candidate; if no single node can satisfy the order, use split
fulfillment only when the order policy permits it.

This design provides a practical balance of fulfillment latency,
operating cost, horizontal scalability, and database complexity. It also
creates a measured path from a simple regional topology to demand-aware
optimization without sacrificing clear inventory ownership.
