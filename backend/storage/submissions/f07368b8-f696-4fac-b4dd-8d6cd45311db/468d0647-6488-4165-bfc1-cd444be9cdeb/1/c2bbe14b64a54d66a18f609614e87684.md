
# Distributed Inventory Caching Strategy for ERP Shards

**Status:** Proposed  
**Scope:** Multi-warehouse ERP inventory reads across geographically distributed fulfillment nodes  
**Decision:** Use Redis Cluster as a distributed read cache, with PostgreSQL remaining the authoritative inventory store.

## 1. Executive Summary

The ERP platform serves high-frequency stock availability queries across multiple warehouse nodes. Directing every read to PostgreSQL increases database load and can add avoidable latency, especially when users and services query inventory across regions.

This document compares Redis Cluster and Memcached, evaluates consistency and partition behavior, defines cache invalidation for concurrent stock changes, and recommends a recoverable cache design.

**Recommendation:** Deploy Redis Cluster with replicas, bounded TTLs, versioned cache entries, and event-driven invalidation. Treat cached stock as advisory only. Every reservation, allocation, or deduction must be validated and committed against the authoritative PostgreSQL inventory shard in a transaction.

A cache hit must never be treated as proof that stock can be reserved.

## 2. Goals and Non-Goals

### Goals

- Reduce latency and database load for repeated stock-level reads.
- Support multiple warehouses and geographically sharded inventory.
- Prevent stale cache values from authorizing overselling.
- Define behavior during concurrent updates, node failures, and network partitions.
- Keep cache recovery independent of authoritative inventory data.

### Non-Goals

- Replacing PostgreSQL as the system of record.
- Making distributed cache state the source of truth for stock.
- Guaranteeing globally linearizable reads from the cache during every network failure.
- Using the cache as the durable record of reservations or stock movements.

## 3. Workload and Design Assumptions

- Inventory ownership is assigned to a warehouse or regional PostgreSQL shard.
- Each SKU at a warehouse has an authoritative available quantity and a monotonically increasing version.
- Reads are much more frequent than stock writes.
- Stock can change concurrently because of orders, returns, transfers, cycle counts, and fulfillment operations.
- A request may query one warehouse or compare availability across several eligible warehouses.
- Network links between regions can become slow or unavailable.

### Suggested Cache Key

```text
inventory:{warehouse_id}:{sku_id}
```

### Suggested Cache Value

```json
{
  "warehouse_id": "WH-001",
  "sku_id": "SKU-1001",
  "available_quantity": 42,
  "version": 108,
  "updated_at": "2026-11-18T10:00:00Z"
}
```

The `version` is generated by the authoritative database transaction. `updated_at` is for observability and freshness checks, not correctness.

## 4. Architecture Options

### Option A — Redis Cluster

Redis Cluster partitions keys across hash slots and supports primary/replica arrangements. It offers data structures, atomic commands, Lua scripting, TTLs, and replication features that are useful for cache coordination.

**Advantages**

- High read throughput and low in-memory access latency.
- Built-in key expiration and configurable eviction policies.
- Replication and automatic failover support.
- Atomic operations and Lua scripts can help implement version-aware cache updates.
- Pub/Sub or Streams can distribute invalidation events, subject to the durability characteristics of the chosen mechanism.
- Hash tags can keep related keys in the same slot when a multi-key operation is required.

**Disadvantages**

- More operational and topology complexity than a single cache node.
- Replication is asynchronous; a failover can lose the most recent cache writes.
- Cluster resharding, failover, and cross-region topology require operational discipline.
- Redis memory overhead can be higher than a simple key/value cache, depending on data structures and configuration.

### Option B — Memcached

Memcached is a distributed in-memory key/value cache. Clients commonly select a server for each key using consistent hashing. Servers do not replicate each other's data by default.

**Advantages**

- Simple key/value model and relatively small per-entry overhead.
- Straightforward horizontal scaling by adding cache nodes and updating client routing.
- Effective for disposable read-through cache entries.
- Low operational complexity for a basic cache tier.

**Disadvantages**

- No built-in replication or cluster-managed failover equivalent to Redis Cluster.
- A node failure causes its keys to become cache misses.
- No native durable event stream for invalidation coordination.
- Limited atomic coordination compared with Redis scripting and data structures.
- Application infrastructure must handle node membership and key redistribution.

## 5. Recommendation Matrix

Scores are qualitative, from 1 (weak) to 5 (strong). They represent fit for this ERP use case, not universal product benchmarks.

| Criterion | Redis Cluster | Memcached |
|---|---:|---:|
| Read latency | 5 | 5 |
| Memory efficiency / footprint | 3 | 5 |
| Replication and failover capability | 4 | 1 |
| Atomic coordination features | 5 | 2 |
| Operational simplicity | 3 | 5 |
| Version-aware invalidation support | 5 | 2 |
| Fit for multi-warehouse recovery | 4 | 2 |

**Interpretation:** Both systems can provide fast reads. Memcached is attractive when cache entries are fully disposable and the application can tolerate broad cache misses. Redis Cluster is the better fit here because coordinated invalidation, replicas, atomic version checks, and controlled failover are more valuable than minimizing cache footprint alone.

## 6. Consistency Model and Source of Truth

Use a **cache-aside** pattern:

1. The API reads the inventory cache.
2. On a cache miss, it reads the owning PostgreSQL shard.
3. It writes the result to cache with a bounded TTL and database version.
4. On a stock mutation, the service commits the database transaction first.
5. After commit, it emits an inventory-change event and invalidates or refreshes the corresponding cache entry.

PostgreSQL is authoritative. Cache entries are snapshots and may be stale for a short period.

### Critical Write Path

A reservation or deduction must not be accepted based only on cached quantity.

Recommended transaction pattern:

```sql
BEGIN;

SELECT available_quantity, version
FROM warehouse_inventory
WHERE warehouse_id = :warehouse_id
  AND sku_id = :sku_id
FOR UPDATE;

-- Validate available_quantity >= requested_quantity.
-- Apply the reservation/deduction and increment version.

UPDATE warehouse_inventory
SET available_quantity = available_quantity - :requested_quantity,
    version = version + 1
WHERE warehouse_id = :warehouse_id
  AND sku_id = :sku_id;

COMMIT;
```

The actual application should validate the requested quantity, use an idempotency key for retryable requests, and record the stock movement in the same transaction or through a reliable transactional-outbox design.

## 7. Cache Invalidation for Concurrent Stock Updates

Multiple fulfillment centers can update inventory concurrently. The design must avoid an older event overwriting a newer cache value.

### Recommended Pattern: Transactional Outbox + Versioned Invalidation

- Update inventory and insert an outbox event in the same PostgreSQL transaction.
- An event publisher delivers committed events to the cache-invalidation consumer.
- Each event contains `warehouse_id`, `sku_id`, `new_version`, and event ID.
- The consumer compares the event version with the cached version.
- If the event is newer, delete the cache key or refresh it from the authoritative shard.
- Duplicate events are safe because event IDs and versions make processing idempotent.
- Periodic reconciliation and TTL expiry provide additional protection if an event is delayed or lost.

For a simple and safe first implementation, **delete-on-write** is preferred over trying to calculate and increment cached stock quantities. The next read repopulates the cache from PostgreSQL.

### Race Condition Protection

Consider this sequence:

1. Reader A loads database version 10.
2. Writer B commits version 11 and invalidates the cache.
3. Reader A attempts to populate the cache with version 10 after the invalidation.

Prevent this stale refill by using a version-aware cache write. A Redis Lua script can compare the incoming version with the cached version and refuse to replace a newer entry. A stronger implementation can maintain a short-lived version/tombstone key so an invalidation arriving before an in-flight stale read prevents that stale value from being reinserted.

If the cache cannot safely establish that the value is current, do not populate it; return the database result for that request and retry cache population later.

### TTL and Eviction Policies

- Use a bounded TTL, for example 30–120 seconds, selected through load testing and business freshness requirements.
- Add randomized TTL jitter to reduce synchronized expiry and cache stampedes.
- Use an eviction policy suitable for a cache, such as Redis `allkeys-lru` or `allkeys-lfu`, after sizing memory and reviewing workload patterns.
- Do not rely on TTL alone for correctness.
- Do not cache reservation authorization decisions.
- Consider shorter TTLs for fast-moving SKUs and longer TTLs for stable catalog metadata.
- Apply request coalescing or a short lock to prevent many simultaneous misses from loading the same key.

## 8. Partition Tolerance and Network Failure Behavior

A distributed cache can become unavailable or inconsistent during network partitions. The ERP must fail safely.

| Failure Scenario | Expected Behavior | Recovery |
|---|---|---|
| Cache node unavailable | Treat as cache miss; read the owning PostgreSQL shard | Reconnect and warm keys gradually |
| Redis primary fails | Allow configured replica promotion; tolerate loss of recent cache writes | Refill missing/stale keys from PostgreSQL |
| Application cannot reach cache but can reach database | Bypass cache for reads; continue authoritative database transactions | Restore cache connectivity and repopulate on demand |
| Region loses connectivity to another region | Do not assume remote cache data is current; read only from the owning shard if reachable | Reconcile through committed inventory events |
| Region cannot reach its owning database shard | Do not confirm reservations or deductions | Retry supported requests with idempotency keys after recovery |
| Invalidation event is delayed or duplicated | Version checks make duplicates harmless; TTL bounds stale cache lifetime | Replay outbox events and reconcile versions |
| Cache is fully flushed | Increased database reads are expected | Rate-limit warming and use gradual prewarming |

### Consistency Choice During Partitions

Prefer **availability for non-binding display reads** only when the UI clearly marks data as potentially stale and includes a freshness indicator.

For operations that promise stock—reservation, order acceptance, allocation, or deduction—prefer correctness over availability: require the authoritative inventory shard to validate and commit the operation.

Do not route a write to a different warehouse's database merely because the owning shard is unreachable. Cross-warehouse fulfillment must follow the explicit routing and ownership rules.

## 9. Multi-Region Deployment

- Keep each warehouse's authoritative inventory in its assigned PostgreSQL shard.
- Deploy Redis cache capacity close to the application services that read it.
- Cache entries should identify the owning warehouse and database version.
- Avoid treating asynchronously replicated cross-region cache data as authoritative.
- For cross-region availability searches, query eligible warehouse owners or use a clearly labelled aggregate/read model with a freshness timestamp.
- Keep cache keys namespaced by environment and tenant where applicable.

## 10. Observability and Operational Controls

Track:

- Cache hit and miss rate by region and warehouse.
- Read latency at p50, p95, and p99.
- Cache connection errors and Redis failovers.
- Invalidation event lag and outbox backlog.
- Version mismatch and stale-refill prevention counts.
- Database load during cache outages and warm-up.
- Eviction rate and memory pressure.
- Reservation conflicts and rejected insufficient-stock attempts.

### Suggested Initial Alerts

- Invalidation lag exceeds the agreed freshness objective.
- Cache hit rate drops sharply for a sustained period.
- Redis memory remains above the configured safe threshold.
- Database read load exceeds the cache-bypass capacity target.
- Cache and database versions repeatedly disagree.

Thresholds should be set after measuring the actual workload rather than treating example values as production SLAs.

## 11. Security and Reliability

- Keep cache endpoints on private networks.
- Require authentication and TLS where supported by the deployment.
- Apply least-privilege access and separate application credentials by environment.
- Do not store payment data, credentials, or unnecessary personal information in cache.
- Set connection, command, and retry timeouts.
- Use bounded retries with exponential backoff and jitter.
- Apply circuit breakers so cache outages do not create retry storms.
- Ensure cache keys include tenant boundaries where the ERP is multi-tenant.

## 12. Final Decision

Adopt **Redis Cluster as a disposable, version-aware cache-aside layer** for high-frequency inventory reads.

The design should:

1. Keep PostgreSQL as the only authority for stock quantities and reservations.
2. Use warehouse-scoped cache keys and database-generated versions.
3. Invalidate after committed writes through a transactional outbox.
4. Make invalidation idempotent and prevent stale readers from overwriting newer values.
5. Use bounded TTLs and an eviction policy such as `allkeys-lru` or `allkeys-lfu`.
6. Bypass cache for correctness-critical writes and fall back to the owning database for cache outages.
7. Fail closed for reservations when the owning database cannot validate stock.

Memcached remains a reasonable alternative for simple, fully disposable cache workloads where replication and coordinated invalidation are not required. For this ERP scenario, Redis Cluster provides the stronger overall balance of latency, coordination, and recovery capability.
